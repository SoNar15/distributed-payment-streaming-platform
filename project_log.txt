## Initial Strategy

The original plan was to execute Spark directly on Windows using the existing Python virtual environment.

```text

```

Core responsibilities:

* Print events to console

---

## Problems Encountered

### Kafka Broker Availability Issue

Error:

```text
kafka.errors.NoBrokersAvailable
```

Cause:

Payment generator was started while Kafka broker was not running.

Impact:

Producer could not establish connection to Kafka.

Resolution:

Verified Kafka startup before launching producers.

Validation:

```text
Kafka Broker Running
Topic Available
Producer Connected
```

---

### Kafka Broker Recovery Issues

Symptoms:

* Kafka failed to restart cleanly
* Topic metadata inconsistencies
* Unexpected broker failures

Cause:

Multiple forced broker shutdowns during development.

Impact:

Spark could not reliably connect to Kafka.

Resolution:

Deleted KRaft metadata directory.

Generated a new Cluster ID:

```cmd
kafka-storage.bat random-uuid
```

Reformatted storage:

```cmd
kafka-storage.bat format
```

Restarted broker with fresh metadata.

---

### Python Environment Confusion

Symptoms:

```text
ModuleNotFoundError
```

and inconsistent package behavior.

Cause:

Git Bash was using global Python instead of project virtual environment.

Verification:

```bash
which python
python -c "import sys; print(sys.executable)"
```

Result:

Global Python was being used.

Resolution:

Validated interpreter path and reinstalled required dependencies.

---

### PySpark Installation Mismatch

Observed:

PySpark installed but Spark jobs failed.

Cause:

Packages existed in global Python but not inside project environment.

Resolution:

Verified installation directly:

```bash
venv/Scripts/python.exe -c "import pyspark"
```

Confirmed:

```text
PySpark 3.5.1
```

installed successfully.

---

### Spark on Windows Challenges

Observed Issues:

* winutils.exe warnings
* Native Hadoop warnings
* Environment variable complexity
* PATH inconsistencies

Engineering Assessment:

Spark functionality worked, but Windows introduced unnecessary operational complexity.

# Spark-Kafka Integration

## Objective

Consume Kafka events directly from Spark Structured Streaming.

Implemented:

```python
.config(
    "spark.jars.packages",
    "org.apache.spark:spark-sql-kafka-0-10_2.12:3.5.1"
)
```

Reason:

Spark does not include Kafka support by default.

Without this package:

```text
Spark cannot read Kafka topics.
```

### Kafka Metadata Timeout

Error:

```text
TimeoutException:
Timed out waiting for a node assignment
```

Cause:

Kafka metadata inconsistency after repeated broker restarts and storage resets.

Resolution:

Performed clean KRaft reinitialization and broker restart.

---

### Streaming Offset Issue

Original configuration:

```python
.option("startingOffsets", "latest")
```

Problem:

Spark only reads events arriving after query startup.

Existing messages were skipped.

Resolution:

Changed to:

```python
.option("startingOffsets", "earliest")
```

Result:

Spark processed existing Kafka messages.

# Additional Lessons Learned

8. Spark Structured Streaming debugging requires validating each layer independently.
9. WSL provides a significantly smoother Spark development experience than Windows.
10. Kafka metadata and storage consistency are critical for stable streaming applications.
11. Environment validation is often more important than writing additional code.
12. Distributed systems fail most often due to integration and configuration issues rather than application logic.
